## Phase 1: Core System Architecture & State Durability

### 1.1 Objective

Build a fault-tolerant state-machine runtime that can recover from container crashes, handle long-running operations, and support Human-in-the-Loop (HITL) approval gates without losing state.

### 1.2 Functional Requirements

* **State Persistence:** Every node transition in the execution graph must be checkpointed to a relational database (**PostgreSQL** via `LangGraph` / `PostgresSaver`).
* **Interrupt & Resume:** High-risk actions (e.g., executing code, mutating database records, executing API write calls) must trigger an `interrupt` state, pause execution, and persist context until an external approval signal is received.
* **Retry Policies & Exponential Backoff:** Network calls and LLM API invocations must implement configurable retries with jitter and exponential backoff to handle rate limits ($HTTP\ 429$) and transient server errors ($HTTP\ 5xx$).

### 1.3 Technical Deliverables

* **Database Schema:** `checkpoints`, `writes`, and `thread_metadata` tables configured in PostgreSQL.
* **State Definition (`TypedDict` / Pydantic):**
* `messages`: Full chat history list.
* `plan`: List of sub-tasks generated by the planner.
* `retrieved_docs`: Array of fetched context objects.
* `next_step`: Identifier for the next execution branch.
* `error_context`: Capture stack traces for self-correction nodes.


* **Human-in-the-Loop Gate:** An API endpoint (`POST /api/v1/threads/{thread_id}/approve`) that resumes an interrupted graph thread.

---

## Phase 2: Dynamic Data Integration & Agentic Retrieval

### 2.1 Objective

Move beyond static vector search by integrating dynamic data connectors via Model Context Protocol (MCP) and implementing multi-step query decomposition with hybrid search.

### 2.2 Functional Requirements

* **Model Context Protocol (MCP) Integration:** Connect agents to external tools (e.g., GitHub, Jira, PostgreSQL) using standardized MCP client/server interfaces.
* **Query Decomposition (Planner Node):** When a complex query arrives, the LLM must generate 1–3 targeted sub-queries.
* **Hybrid Search Retrieval:**
* **Dense Retrieval:** Vector embeddings stored in **pgvector** or **Qdrant**.
* **Sparse Retrieval:** BM25 keyword search.
* **Reciprocal Rank Fusion (RRF):** Combine dense and sparse scores before passing results to a cross-encoder re-ranker.


* **Dual-Layer Memory:**
* **Short-Term Memory:** Thread-level conversation buffer stored in Redis/Postgres.
* **Long-Term Memory:** Semantic user preference/fact store extracted asynchronously via entity extraction.



### 2.3 Technical Deliverables

* **MCP Client Setup:** Integration module capable of calling external tools over stdio/HTTP.
* **Retrieval Pipeline Module:** Multi-step pipeline executing: `Decompose Query -> Hybrid Search -> RRF Rerank -> Cross-Encoder -> Top-K Context`.

## Phase 3: OpenTelemetry Traceability & System Observability

### 3.1 Objective

Instrument the entire agent execution chain using vendor-neutral OpenTelemetry standards to capture latency, token usage, execution spans, and system costs.

### 3.2 Functional Requirements

* **Standardized Instrumentation:** Instrument all LLM calls, vector database queries, tool executions, and state node transitions using **OpenInference / OpenTelemetry**.
* **Span Hierarchy:** Ensure parent-child relationships are preserved across execution threads:
```text
[Root Span: Thread Run]
 ├── [Span: Planner Agent]
 │    └── [LLM Call: Query Decomposition]
 ├── [Span: Hybrid Retriever]
 │    ├── [Vector DB Search Span]
 │    └── [BM25 Search Span]
 └── [Span: Tool Call Execution (MCP)]

```


* **Observability Dashboard Integration:** Export all traces and spans to an observability platform (**Langfuse** or **Arize Phoenix**).
* **Metric Aggregation:** Capture and monitor:
* Latency per node ($p_{50}$, $p_{90}$, $p_{99}$).
* Input/Output Token counts broken down by model provider.
* Estimated execution cost per run ($/request).



### 3.3 Technical Deliverables

* **Tracing Middleware:** Auto-instrumentation setup decorating graph nodes and tool calls.
* **Live Dashboards:** Configured views for trace inspection, cost breakdown, and latency distribution.

## Phase 4: Continuous Evaluation & CI/CD Quality Gates

### 4.1 Objective

Implement automated pre-deployment and post-deployment evaluation suites to guarantee answer quality, prevent regression, and measure system safety.

### 4.2 Functional Requirements

* **Golden Dataset:** A curated benchmark set of 50–100 evaluation cases containing:
* Input queries.
* Ground truth context / expected citations.
* Reference answers.
* Adversarial prompt injection attacks.


* **Evaluation Metrics (DeepEval / Ragas):**
* **Faithfulness:** Degree to which the answer is derived *only* from context ($0.0 - 1.0$).
* **Answer Relevance:** How well the output addresses the query ($0.0 - 1.0$).
* **Context Precision & Recall:** Quality and completeness of retrieved chunks.
* **Hallucination Rate:** Frequency of non-grounded claims.


* **Automated CI/CD Pipeline:** Run evaluations via **GitHub Actions** on every Pull Request. Enforce a hard quality gate (e.g., build fails if Faithfulness falls below 0.85).
* **Online LLM-as-a-Judge:** Sample 10% of live production traces logged to Langfuse and evaluate them asynchronously using a judge model (e.g., GPT-4o / Claude 3.5 Sonnet).

### 4.3 Technical Deliverables

* **`eval_suite.py` Script:** Test runner calculating DeepEval/Ragas metrics.
* **GitHub Actions Workflow (`.github/workflows/eval.yml`):** Automated trigger executing test suites and commenting evaluation scores directly on Pull Requests.

---

## Phase 5: Production Security & Input/Output Guardrails

### 5.1 Objective

Protect the platform against malicious prompt injections, prevent PII leakage, and validate structured outputs.

### 5.2 Functional Requirements

* **Input Guardrails:**
* Detect and block prompt injection attempts (e.g., using `Llama Guard` or regex/classifier models).
* Automatically redact PII (SSNs, emails, credit cards) before sending prompts to external LLMs.


* **Output Guardrails:**
* Validate output against strict JSON/Pydantic schemas.
* Citation Verification: Ensure every claim in the final answer is mapped back to a valid document chunk ID.


* **Action Authorization:** Implement scope-based permissions ensuring the agent cannot execute actions beyond the authenticated user's authorization level.

### 5.3 Technical Deliverables

* **Guardrail Middleware Layer:** Interceptor executing input scans *before* graph execution and output validation *before* returning HTTP responses.
