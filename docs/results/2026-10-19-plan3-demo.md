# Plan 3 demos: live tools, human-in-the-loop, crash recovery (2026-10-19)

**Setup:** real `copilot serve` (FastAPI + uvicorn) driving:
- Postgres (ParadeDB);
- two GitHub MCP containers (`ghcr.io/github/github-mcp-server:v2.0.2`):
  - read client: read-only mode with the read token;
  - write client: `add_issue_comment` / `issue_write` only, with a token scoped to `pavankalyan-5/copilot-sandbox`;
- the local reranker and OpenAI.

The client is [`scripts/demo_service.py`](../../scripts/demo_service.py), which talks plain HTTP + SSE like any client would. For the crash demo, the lease was shortened to 10 s and the recovery check to every 3 s (defaults: 60 s / 15 s).

**Total cost of all three demos: about $0.003.** Project total: $0.0229 of the $10 budget.

## Demo 1: live lookup

> **Q:** Is PR #3564 merged, and who opened it?

```
+3.31s  Planning searches
+4.68s  Checking GitHub        ← issue_read/pull_request_read through MCP, read-only
+6.34s  Writing the answer → Verifying citations → Done
```
> PR #3564 is closed but not merged, and it was opened by the user Kludex [9000000].
> Source: [9000000] live_pr #3564 — https://github.com/Kludex/starlette/pull/3564

This is the exact question the agent got **wrong** in plan 2's first run, when it said "merged". It was answered from the index without state metadata. Now it's fetched live and cited (`9000000` = the first live result).

## Demo 2: human-in-the-loop action, posted exactly once

> **Q:** Comment on issue #1 with a short summary of how to run code when a Starlette app starts up and shuts down.

| Step | Result |
|---|---|
| Ask | `202`. The graph ran plan → retrieve → … → **propose_action**, then **paused** (`awaiting_approval`). The pending card showed `comment_on_issue on #1 in pavankalyan-5/copilot-sandbox` with the drafted body. |
| GitHub before approval | **0 comments** on sandbox issue #1 |
| `POST /approve` (maintainer key) | `202` → *Posting to GitHub* → `done`, `action_result: executed` |
| `POST /approve` again (double click) | **`409`** *"nothing is waiting for approval (already decided?)"* |
| GitHub after | **exactly 1 comment**: [copilot-sandbox#1](https://github.com/pavankalyan-5/copilot-sandbox/issues/1#issuecomment-6270462134) |
| `actions` table | 1 row, `executed`, `decided_by = key:b3c2572e1a` (a hash of the key, never the key itself) |

**Found by the real run:** `action_result.url` came back `None`.
- **Cause:** the test fakes returned `html_url`, but GitHub's MCP server v2.0.2 returns `MinimalResponse {"id", "url"}`, sometimes nested. Confirmed by reading its source (`pkg/github/issues.go`).
- **Fix:** URL extraction handles all of these shapes and accepts only `https://github.com/…` page links. Both fakes now return the real shape, and 6 tests were added.

## Demo 3: `kill -9` mid-answer, then automatic resume

> **Q:** How do I serve static files with a StaticFiles mount in Starlette, and can it serve an index.html for directories?

```
+ 3.60s  event: Planning searches
+ 3.60s  💥 kill -9 sent to the server            (process group killed, no cleanup)
         DB after crash: status=running, lease expires in 9.7s
+ 6.20s  new server process up                     (startup recovery: lease still valid → skipped)
         status right after restart: running
+33.19s  status → done (29.6s after the crash)      ← resumed by the periodic recovery check
```

The answer was correct: a `Mount('/static', app=StaticFiles(directory='static'))` example plus `html=True` for `index.html`, cited to the `staticfiles` docs. The thread holds exactly one `user` and one `assistant` message.

**Where the 29.6 s went** (from `llm_usage` timestamps):

| Time | Event |
|---|---|
| 15:13:09 | planner call finished (the last node checkpointed before the crash) |
| ~15:13:19 | lease expired |
| ~15:13:21–24 | periodic check claimed the run in the new process, which **continued from the checkpoint** (sub-query embeddings; the planner was *not* called again) |
| 15:13:25 → 15:13:39 | cold reranker load + `gpt-4.1-mini` writing a 287-token answer (≈12 s of OpenAI latency) |
| 15:13:42 | done |

So **recovery latency is bounded by the lease** (about 12 s here, about 60–75 s with production defaults). The rest is ordinary answer time.

**Found while preparing this demo:** recovery originally ran only at startup. After a quick restart (lease not yet expired), a crashed run would have stayed `running` forever. A periodic recovery loop was added, with its first pass kept synchronous before serving requests. Two tests cover it, and this demo exercised exactly that path.

## What these demos prove

| Claim | Evidence |
|---|---|
| Live data beats a stale index for status questions | Demo 1 |
| Writes need a human, target only the sandbox, and execute once | Demo 2: 0 → 1 comment, second approve → 409, one `actions` row |
| Runs survive a hard crash without redoing finished work | Demo 3: planner called once, run finished after `kill -9` |
| Fakes can drift from real services, so test against reality too | Two real bugs found only by running against real GitHub (`url` shape, quick-restart recovery) |

## After the independent review (same day)

The review found recovery and run-state gaps that the demos above didn't trigger. Fixed test-first (269 tests):

| Gap | Fix |
|---|---|
| A slow node outliving its lease looked dead, so it could be run twice | Heartbeat renews the lease *while* a run is in progress (own DB connection, overall deadline) |
| A worker that lost its lease could still overwrite status | Fencing token (`lease_owner`): renewals and status writes require it; a fenced-out worker stops at the next node |
| A queued or in-process run could be "recovered" by its own server | In-flight set from submit time; recovery skips it |
| `failed` was a dead end; an approved-but-unposted action could be silently discarded | `retry` (API + UI button) continues from the checkpoint; new questions are refused while an action is unfinished |
| Crash right after `202` lost the question; the page showed the previous answer | The question is stored with the claim; recovery replays it, or marks an already-finished turn done |
| Crash between claiming an action and recording it left `pending` forever | Hidden marker plus reconciliation via the read client; ambiguous failures (timeouts) are `unknown`, not `failed` |
| MCP container death disabled tools until restart; plain-text replies crashed runs | Automatic reconnect; replies validated |
| Any key could read any thread; 32-bit ids | Owner per thread (readers see their own; others are 404); 128-bit ids |
| Chat page: citation markup could leak into link URLs; page frameable | Citations before links; github.com-only source links; CSP with `frame-ancestors 'none'` |

The `kill -9` demo was re-run on the new runner: resumed and finished **17.9 s** after the crash (10 s demo lease), logged *"recovering thread … (its previous worker stopped renewing the lease)"*, and ended with the lease released and the saved question cleared.
