# First real agent runs: findings (2026-10-19)

**Setup:** index of `Kludex/starlette` (30 doc pages and 125 issues/PRs, 582 chunks). Planner `gpt-4.1-nano`, answer model `gpt-4.1-mini`, reranker `Xenova/ms-marco-MiniLM-L-6-v2`, top 4 kept per sub-query.

**Raw reports:**
- Every sub-query, all 10 candidates with reranker scores, answers, sources, cost, and time.
- [Run 1 (11:30)](2026-10-19-1130-agent-run.md): no reranker cutoff, no metadata in context.
- [Run 2 (12:37)](2026-10-19-1237-agent-run.md): cutoff −1.0, state and author in context.
- [Run 3 (13:05)](2026-10-19-1305-agent-run.md): after the code-review fixes (citation checking ignores code and requires at least one valid citation; chunk attributes are escaped). Same answers, mostly served from cache.
- Re-run with `uv run python scripts/agent_report.py`.

## Finding 1: the model guessed metadata it was never shown (fixed)

In run 1, Q4 said PR #3564 "was merged". The database says **closed (not merged), author Kludex**.
- **Cause:** state and author were stored in `documents`, but the model only ever saw chunk *text*.
- **Why the citation check didn't catch it:** it checks *which* chunk is cited, not whether the claim is true.
- **Fix:**
  - search results now carry `state` and `author`;
  - chunks render as `<chunk … state="closed" author="Kludex">`;
  - the answer prompt says these attributes are authoritative, and that "closed" ≠ "merged".
  - Tests: `test_hits_carry_state_and_author`, `test_context_exposes_state_and_author`.

## Finding 2: prompting reduces errors but doesn't remove them (open)

In run 2, Q3 wrote "closed but merged" even though `state="closed"` was in its context. This is the kind of error **claim-level citation verification** (plan 5) is designed to catch, and the eval suite (plan 4) will measure how often it happens. We deliberately did **not** tune the prompt until this one example passed, because that would be overfitting to one question.

## How the reranker cutoff was chosen

1. **Recorded everything.** For every planner sub-query, the report re-scores **all 10** hybrid-search candidates (kept and dropped). The reranker runs locally and the sub-query embeddings are cached, so this costs $0.
2. **Labelled candidates** relevant or irrelevant to the user's question, by reading each preview.
3. **Compared the score ranges** (run 1, 7 questions, 110 candidate scores):

   | Group | Score range | Examples |
   |---|---|---|
   | Relevant, well-phrased sub-query | **−0.48 to +5.2** | lifespan docs 0.63 / 2.87 · `max_body_size` 5.2 · `RequestBodyLimitMiddleware` 4.35 · PR #3564 2.76 · auth docs 4.21 |
   | Irrelevant | **≤ −1.14** | config −1.65 · Contributing −1.67 · README −2.1 · GZip −3.99 · "Version 1.9.0" PR −1.14 |
   | On-topic but not what was asked | +2.4 to +3.4 | Benchmarks "Multipart forms" 3.37 · PR #3565 (GZip trailers) 2.39 |

4. **Picked −1.0.** It sits in the gap between the first two groups.
   - Below it are only chunks that would add noise and cost.
   - No cutoff can separate the third group, because the reranker genuinely finds those chunks relevant. Rejecting them is the LLM's job and, later, claim verification's.
5. **Checked the effect** in run 2:
   - Q1 sent **1 chunk instead of 9**.
   - Q4's sub-query "is PR #3564 merged" (filtered to merged PRs, which correctly excludes the closed #3564) now contributes **no** chunks instead of 4 unrelated release PRs.
   - Answer quality held, and cost per question fell (Q1: $0.00119 → $0.00052).

**Caveats:**
- 7 questions is a small sample, so −1.0 is **provisional**. The plan-4 golden set will measure hit rate with and without the cutoff.
- Scores depend on how the *sub-query* is phrased. In Q2, the planner's generic "in a web framework" sub-queries pushed even relevant chunks below −2. Other sub-queries covered them, and better planner prompting is a candidate improvement.

## Other observations

- **The planner over-decomposes simple questions.** Q2 got 3 sub-queries, two of them generic ("web framework or server configuration"). This costs a little extra and adds no new information.
- **Inline citations are sometimes skipped.** In Q3, the model listed `cited_chunk_ids` but put no `[id]` markers in the text. Sources still show correctly. Plan 5's claim verification will enforce per-sentence citations.
- **One PR can appear twice in sources** when two of its chunks are cited. Grouping sources by document is a UI improvement for later.
- **Speed:** 2–5 s per new question (two LLM calls dominate), under 1 s when cached. The reranker takes about 40 ms for 30 candidates.
- **The cache works end to end:** a repeated question in a new thread costs exactly $0.
